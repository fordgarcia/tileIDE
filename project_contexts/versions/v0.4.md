# v0.4 — Run / Debug + Toolchains

> **Status:** planned · Depends on: v0.2 (config) and the LSP/DAP clients (debug adapters are separate programs the user installs; plugins can ship them).

## Goal
F5 works. Users can optionally link installed compilers/runtimes so run and debug function, without TileIDE bundling any.

## Scope
- **Toolchain resolver:** scans PATH and known directories, honours per-workspace pins, and shows what it found.
- **Toolchain manager** UI: detected Python, JDK, GCC/Clang, Node, etc.; pin per workspace; friendly "missing" state with the distro's install command (never installs silently).
- **Run button + launch configs** (written in the same Lua config where possible).
- **Debugging via DAP:** breakpoints, call stack, variables, debug console, debug toolbar.
- Run/debug output opens as **tiles** in the code region (no dedicated bottom panel).
- First-class paths: Python, Java (JDK), C/C++, Node. Others come through plugins or user-installed servers.

## Out of scope
Bundling compilers, auto-installing toolchains, remote debugging, containers.

## Exit criteria
- [ ] A fresh user with Python installed can open a folder, press F5, hit a breakpoint.
- [ ] Same for a JDK project and a C project.
- [ ] Missing toolchain produces a clear message and one actionable next step.

## Risks
- Debug quality depends on a debug adapter existing for the language; TileIDE can only point to it.
- Multiple versions of one runtime (system Python vs venv vs pyenv/mise). Decide which resolution order wins and document it.

## Open questions
- Should toolchain detection read environment managers (mise, asdf, pyenv, nix) from the start, or only PATH?
